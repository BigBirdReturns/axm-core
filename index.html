§01 What Core Does

Three subsystems.
One runtime.

axm-core is the hub package. It neither signs shards (that's axm-genesis) nor produces them from conversations (that's a spoke). It does one thing: verifies sealed Genesis v1 shard directories — canonical JSONL tables under a signed manifest — loads them into a queryable relational database, and lets you ask it questions in English.

⚡
Spectra

Query engine. Every mount is gated by axm-verify — no exceptions in production. Natural language becomes parameterized SQL through deterministic keyword/regex rules (axiom_runtime.nlquery), executed against DuckDB behind a read-only SQL gate. No LLM anywhere in the query path.

⚒
Forge

Document compiler. Takes markdown, plain text, and chat exports. Deterministic tier 0/1 extractors (tables, statutory numbering, cross-references) plus optional tier 3 LLM extraction via Ollama. Delegates signing and Merkle construction to axm-genesis via compile_generic_shard. Never reimplements the kernel.

⬡
DuckDB Runtime

The query substrate. At mount time the shard's JSONL tables are parsed and loaded into DuckDB: per-shard tables plus cross-shard UNION ALL views (claims, entities, provenance, spans). A rebuildable cache outside the sealed shard, which is never written to. In memory. No server.

§02 Spectra Query Engine

Language in.
SQL out.
No LLM.

Spectra is deliberately not a RAG system. It doesn't embed your query, search for similar chunks, and ask an LLM to synthesize them. That path is expensive and non-deterministic.

Instead: your natural language query is matched by deterministic keyword and regex rules into a query shape. The rules emit parameterized SQL — user-derived values are bound as ? parameters, never interpolated. DuckDB executes it. The output is a result set — structured, reproducible, auditable.

There is no LLM in this path at all — not at query time, not at index time. The only thing that runs is SQL, behind a read-only gate.

Input
Natural Language Query

"What treats severe bleeding?"

Rule Router
Keyword Classification

Regex + keyword rules in axiom_runtime.nlquery pick a query shape — search, decision lifecycle, temporal, lineage. No LLM call.

Parameterized SQL
DuckDB Execution

Values bound as ? parameters. The read-only SQL gate rejects anything but reads. Query executes against the mounted JSONL-backed tables. Zero injection surface.

Output
Structured Result Set

Rows returned. Same query. Same shards. Same output. Always.

axiom_runtime/nlquery.py — run against the gold shard 
# Real session — executed against the gold shard fm21-11-hemorrhage-v2
from axiom_runtime.engine import SpectraEngine
from axiom_runtime.nlquery import natural_language_to_query

engine = SpectraEngine()  # hard gate: axm-verify must pass before mount
engine.mount("../axm-genesis/shards/gold/fm21-11-hemorrhage-v2", None)

sql, params = natural_language_to_query("what treats severe bleeding")
# sql    → SELECT DISTINCT COALESCE(se.label, c.subject) AS subject,
#            c.predicate, COALESCE(oe.label, c.object) AS object, c.tier
#          FROM claims c LEFT JOIN entities se ... WHERE ... LIKE ?
# params → ['%treats%', '%treats%', '%severe%', ..., 50]  — bound, never inlined

rows = engine.con.execute(sql, params).fetchall()
# → 3 rows in 3.8 ms:
#   ('direct pressure',  'treats', 'severe bleeding', 3)
#   ('pressure dressing','treats', 'severe bleeding', 3)
#   ('tourniquet',       'treats', 'severe bleeding', 3)
§03 Forge

Documents
become shards.

Forge is the document ingestion pipeline. You point it at a document. Deterministic tier 0/1 extractors lift structure (tables, headings, statutory numbering, cross-references); tier 3 optionally adds LLM extraction via Ollama. Then it delegates all signing and Merkle construction to compile_generic_shard. Forge never reimplements the kernel.

The output is structurally identical to a chat shard. Same manifest.json — with no shard_id field: identity is derived as sh1_ + BLAKE3(canonical manifest bytes). Same canonical JSONL tables. Same verification path. Forge doesn't know it's compiling a field manual versus a legal statute versus a design document. It applies the same protocol to all of them.

01
Extract

Tier 0/1 extractors lift markdown tables, headings, statutory numbering, and cross-references into claim candidates. Tier 3 (optional) adds LLM extraction.

→ .forge_work/candidates.jsonl
02
Hash

BLAKE3 over every sealed file. Merkle tree with RFC 6962 odd-leaf promotion and domain separation. Root committed in the manifest.

→ integrity.merkle_root
03
Sign

axm-genesis signs the canonical manifest bytes via compile_generic_shard with axm-hybrid1 (Ed25519 ‖ ML-DSA-44 — both must verify). 1344-byte public key, 2484-byte signature; keys from axm-build keygen.

→ sig/manifest.sig · sig/publisher.pub
04
Write

Canonical JSONL tables written: graph/entities.jsonl, graph/claims.jsonl, graph/provenance.jsonl, evidence/spans.jsonl — plus content/ source bytes. Shard directory sealed; no Parquet inside.

→ <output>/shard/ · id = sh1_ + BLAKE3(manifest)

§04 DuckDB Runtime

Every shard.
One database.
No server.

DuckDB runs in-process. There is no separate database server to start, configure, or migrate. When a shard is mounted, Spectra parses its canonical JSONL tables with the stdlib JSON reader and loads them into DuckDB: per-shard tables keyed by the derived shard identity, plus cross-shard UNION ALL views.

The loaded tables are a rebuildable cache that lives outside the shard — the sealed directory is never written to. And the mount is gated: axm-verify must pass first. A shard that doesn't verify doesn't mount.

Spectra mount pattern — real session, two shards 
from axiom_runtime.engine import SpectraEngine

engine = SpectraEngine()

# Hard gate: Shard → (Clarion decrypt) → axm-verify → Mount → Query
engine.mount("../axm-genesis/shards/gold/fm21-11-hemorrhage-v2", None)
engine.mount("./out/shard/shard", None)  # the shard Forge just built

# Each mount creates per-shard tables keyed by the derived identity:
#   claims__1b98b02bdb0b__sh1_ec77b88475889e48a7cd...
# and rebuilds the cross-shard union views:
#   claims · entities · provenance · spans
#   (+ temporal · lineage · refs when shards ship those ext/ tables)

engine.con.execute("SELECT count(*) FROM claims").fetchone()
# → (9,)  — 6 gold claims + 3 forged claims, one view, 1.6 ms

# Unknown or binary ext/ formats are skipped with a log line —
# ext/ is opaque to the kernel. Unmount rebuilds the views without the shard.
§05 Cross-Shard Joins

Every shard can
reference every other.

The ext/references@1.jsonl table carries pointers into other shards by derived shard identity (sh1_<64 hex>) and target claim/entity id. DuckDB resolves these at query time without a central registry — see examples/query_cross_shard.py for the full two-shard composition.

ext/references@1.jsonl — registry schema 
-- One row per cross-shard link (EXTENSIONS_REGISTRY.md)
src_claim_id     VARCHAR  -- claim in THIS shard
relation_type    VARCHAR  -- supports | contradicts |
                          -- derives_from | supersedes | cites
dst_shard_id     VARCHAR  -- target identity, sh1_<64 hex>
dst_object_type  VARCHAR  -- claim | entity | shard
dst_object_id    VARCHAR  -- target claim_id / entity_id
confidence       VARCHAR  -- decimal string in [0,1]
note             VARCHAR  -- "" if none
Evidence join — run against the gold shard 
-- Every claim with its sealed evidence text
SELECT c.claim_id, s.text AS evidence
FROM claims c
JOIN provenance p ON c.claim_id = p.claim_id
JOIN spans s ON p.source_hash = s.source_hash
          AND p.byte_start  = s.byte_start
          AND p.byte_end    = s.byte_end;

-- ✓ 3 rows · 3.0 ms — e.g.
-- c1_6sdyun7gz4vhk6elt6mnz... →
--   "tourniquet can be used to control
--    bleeding from a limb. It should not …"
ext/lineage@1.jsonl — supersession record 
-- Registry schema (EXTENSIONS_REGISTRY.md). Note what is NOT here:
-- a shard's own id. Identity is derived from the manifest bytes
-- (sh1_ + BLAKE3) and never appears inside the shard's own files.
supersedes_shard_id  VARCHAR  -- predecessor, sh1_<64 hex> form
action               VARCHAR  -- supersede | amend | retract
timestamp            VARCHAR  -- RFC 3339
note                 VARCHAR  -- "" if none

-- The manifest's own `supersedes` array uses the same sh1_ form —
-- each element MUST match ^sh1_[0-9a-f]{64}$ (spec section 6).
-- Spectra mounts this table into the cross-shard `lineage` union view.
§06 Query Examples

Ask in English.
Get rows.

Every query below was actually executed against the gold shard fm21-11-hemorrhage-v2 (the union-count card also mounts the Forge-built shard from §03). Row counts and timings are from those runs. NL queries go through natural_language_to_query; no LLM call anywhere.

>>> natural_language_to_query("what treats severe bleeding")
SELECT DISTINCT COALESCE(se.label, c.subject) AS subject, c.predicate, COALESCE(oe.label, c.object) AS object, c.tier FROM claims c LEFT JOIN entities se ON c.subject = se.entity_id LEFT JOIN entities oe ON c.object = oe.entity_id WHERE ... LIKE ? -- bound params, abridged
✓ 3 rows · 3.8ms — direct pressure · pressure dressing · tourniquet
>>> natural_language_to_query("find tourniquet")
-- same label-join shape, params ['%tourniquet%', ...] SELECT DISTINCT ... FROM claims c LEFT JOIN entities se ... WHERE ... LIKE ?
✓ 2 rows · 4.0ms — treats severe bleeding · contraindicated_for broken bone
>>> Predicate histogram over the claims union view
SELECT predicate, count(*) AS n FROM claims GROUP BY 1 ORDER BY n DESC
✓ treats 3 · supports 2 · contraindicated_for 1 · 4.9ms
>>> Resolve entity ids to labels
SELECT se.label AS subject, c.predicate, oe.label AS object FROM claims c JOIN entities se ON c.subject = se.entity_id JOIN entities oe ON c.object = oe.entity_id WHERE c.predicate = 'treats'
✓ 3 rows · 3.2ms — ids are e1_/c1_ full-digest base32
>>> Claims joined to their sealed evidence bytes
SELECT c.claim_id, s.text AS evidence FROM claims c JOIN provenance p ON c.claim_id = p.claim_id JOIN spans s ON p.source_hash = s.source_hash AND p.byte_start = s.byte_start AND p.byte_end = s.byte_end
✓ 3 rows · 3.0ms — every claim traceable to source bytes
>>> Cross-shard union — gold shard + freshly forged shard
-- after engine.mount(...) × 2 SELECT count(*) FROM claims
✓ (9,) · 1.6ms — 6 gold + 3 forged claims in one view
